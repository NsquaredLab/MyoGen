
### Objective

Use memory when it provides a computational benefit while preserving available headroom for the operating system and other applications.

The earlier fixed 8 GB simulation ceiling is superseded by this policy.

### Memory measurements

Add a small direct dependency on `psutil` for portable system and process measurements.

Use **available physical memory**, rather than unused memory or swap capacity. Available memory includes reclaimable memory and is the recommended cross-platform pressure indicator. [psutil documentation](https://psutil.io/api/#psutil.virtual_memory)

Record:

- Total and available physical memory.
- Parent and worker memory.
- Managed retained buffers.
- Pending allocation reservations.
- Active workers and batch sizes.
- Cache occupancy and pressure events.

Do not sum shared array sizes repeatedly in the managed-buffer ledger. Report aggregate process RSS separately, noting that it can double-count shared pages.

### Default reserve and allocation allowance

Define:

```text
system_reserve = max(4 GiB, 20% of physical RAM)

headroom = max(0, available_memory - system_reserve)

allocation_margin = max(512 MiB, 10% of headroom)

new_allocation_allowance =
    max(0, headroom - allocation_margin - pending_growth)
```

Apply any user-specified numerical-buffer ceiling as an additional restriction.

`pending_growth` means allocations promised to workers but not yet reflected in the current memory measurement. It must not include memory already represented in that measurement.

Examples before new allocations:

| Machine state | Reserve | Approximate additional allowance |
|---|---:|---:|
| 16 GiB RAM, 12 GiB available | 4 GiB | 7.2 GiB |
| 16 GiB RAM, 8 GiB available | 4 GiB | 3.5 GiB |
| 32 GiB RAM, 24 GiB available | 6.4 GiB | 15.84 GiB |

These are admission estimates, not advance allocations or guaranteed process limits.

### Controller and worker coordination

Implement one controller per optimized simulation call.

The controller owns admission decisions for all workers. Individual workers must not independently claim a percentage of system RAM.

For each work item:

1. Estimate incremental peak memory, including temporary arrays, result transport, and retained outputs.
2. Obtain a controller reservation before dispatch.
3. Account for allocations as they become resident.
4. Return unused reservations after completion or failure.
5. Retain the accounting for outputs that remain alive.

Refresh memory before dispatch and monitor it every second during execution.

Bound joblib dispatch to admitted work. Use `batch_size=1` for outer scheduling and prevent an uncontrolled queue of prefetched MU jobs. Internal fibre and convolution batches remain separately sized.

### Adaptive behavior

Start with at most two workers and a conservative batch size.

Increase batch size only when:

- A larger batch would reduce computational overhead.
- Its estimated peak fits.
- At least five consecutive one-second measurements show sufficient headroom.
- The previous batch completed successfully.

Increase by at most 25% per adjustment. Keep worker count at or below the policy and `n_jobs` limits.

When available memory falls below the reserve plus allocation margin:

1. Stop dispatching additional work.
2. Evict unused in-memory caches.
3. Request smaller subsequent batches.
4. Reduce active concurrency as workers reach safe boundaries.
5. Resume only after sufficient memory is available.

Never terminate another application or change its priority.

### Safe boundaries and allocation failures

Workers respond between fibre batches, convolution blocks, or completed MU calculations. A running numerical-library operation cannot always be interrupted immediately.

Each batch must commit its contribution only after successful completion. A failed retry must not double-add part of a MUAP or consume additional random draws.

On a recoverable allocation failure:

- Release failed-batch temporaries.
- Halve the batch size.
- Retry the same work with the same inputs.
- Stop after failure at the smallest supported batch.

Do not use allocation failures as the normal sizing mechanism.

Unlike the existing anatomical helper, the new scheduler must permit **zero admitted jobs** when even one item cannot fit.

### Required inputs and results

Separate memory into:

- **Required:** realized inputs, necessary prepared operators, output arrays, active accumulators.
- **Adjustable:** batch buffers, concurrent workers, unused caches, queued work.

If required storage plus the smallest working batch cannot fit, raise `MemoryBudgetError` before starting the affected stage.

If external pressure blocks progress during a run, wait up to 60 seconds while releasing adjustable memory. Then raise `MemoryBudgetError`, reporting:

- Required minimum working set.
- Measured available memory.
- Configured reserve and optional ceiling.
- Completed work and persistent-cache availability.

Completed cached MUs remain reusable. An incomplete final EMG must not be published as a successful result.

### User reporting

Provide a read-only `execution_report` after success or failure containing:

- Policy and selected backend.
- Stage timings.
- Minimum observed available memory.
- Peak observed process memory.
- Initial and final batch sizes.
- Worker-count changes.
- Cache hits and evictions.
- Pressure pauses and allocation retries.
- Completion status.

Aggregate repeated events instead of producing a log entry every second.
